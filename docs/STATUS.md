  3. Reseed with `npm run seed`. The backend's tables and the checkpointer's are now in the `payrollcheck` schema, and seeding on Supabase drops the old `undercover` schema with everything in it, saved progress included, since renamed graph nodes, state keys and thread names make old checkpoints unreadable. The SQLite file is now `payrollcheck.db`.

  Each browser forgets its saved appearance and the Copilot sidebar's state once, since their keys are now `payrollcheck-*`. Anything deployed from the course under the old names (a Gateway with `undercover-app` and `undercover-context` targets, the `undercover_*` Memories, the `UNDERCOVER_API_KEY` credential, the `undercover` AgentCore project) no longer matches and would need provisioning again; stage 7's runbook uses the new names.
- After pulling the security changes, reseed with `npm run seed`: a case signed off but not yet paid under the old flow can't be paid any more.
- `.env` needs `PAYROLLCHECK_API_KEY`, the agent's API key, a random value of at least 32 characters such as one from `secrets.token_urlsafe(32)`; the agent doesn't get ready without it.
- After pulling the context layer, reseed with `npm run seed`: the documents table has a version, and the decisions and steps have new columns.
- After pulling the send back and the agent on Runtime, reseed with `npm run seed`: cases, runs and rounds have new columns, and there are `sent_back_decisions` and `locks` tables.

- `npm run dev` starts the backend on port 8000, the agent's AgentCore app on port 8080 (stop Lab 1's `agentcore dev` first, which uses the same port), the Copilot's AgentCore app on 127.0.0.1:8081, the context layer on port 8006 (`uv run -m context`, at http://127.0.0.1:8006/mcp) and the dashboard on http://localhost:5173. It passes `.env` to the backend, the agent and the Copilot, so it needs a `.env`. - `npm run seed` rebuilds the database `npm run dev` uses from `data/`, with the plans and the two documents from `context/`, putting every case back in the queue and emptying the dispatches and evaluations. - Every page needs a signed-in reviewer. Sign in on `/sign-in` with a reviewer's email from `data/reviewers.json` and the password set for them in Supabase Auth (`REVIEWER_PASSWORD` in `.env`). There's no sign-up. Dana Whitfield is the only reviewer who can sign off payouts over the limit.
- `npm run build` builds the dashboard into `dashboard/dist`, with the Supabase address and publishable key from `.env`. When the folder exists, the backend serves it at `/` beside the API, so `uv run --env-file .env -m uvicorn backend.main:app` alone serves the whole app at http://127.0.0.1:8000; `npm run dev` is unchanged. `docs/TECH_STACK.md` describes the deployment.
- On the queue page, choose the payroll agents at once, from 1 to 25, and press Start a dispatch. The app creates the dispatch and asks the agent to work it, and the agent works every case in progress, waiting or sent back with up to N payroll agents at once. Only one dispatch, evaluation or working round goes at a time; a start while one is going says what is going, and a start while the agent isn't running says so and leaves the dispatch stopped with that reason. ## Built

- `backend/`: the database is seeded from `data/`, with the plans and the two documents from `context/`, and created on startup when it has no tables. Only seeding reads `data/evals/`. A test checks that every operation follows the API rules. `main.py` holds the app and the case, document and reviewer operations; `runs.py` is an `APIRouter` with every operation under `/api/runs`, `/api/dispatches` and `/api/evaluations`; `configuration.py` is an `APIRouter` with the payroll agent's versions; `improvement.py` is an `APIRouter` with the rounds of the improver, the agent's operations under `/api/rounds` and the dashboard's under `/api/improvement`. They share the `Database` and `SignedIn` dependencies in `dependencies.py`, `to_case()` and `to_summary()` in `views.py`, finding a run or a version and the not-found messages in `lookups.py`, reading runs in `scoreboard.py` and `now()` in `database.py`, and no router uses another's helpers. Case and run statuses, decisions, run kinds and labeled sets are `StrEnum`s in `models.py`.
  - On AWS Lambda: `handler` at the end of `backend/main.py` is the app through Mangum, with the startup hook off, so nothing seeds the database there. With `AWS_LAMBDA_FUNCTION_NAME` set, `engine_for` opens Postgres with a connection for each request and none kept (`NullPool`) and prepared statements off (`prepare_threshold=None`), for Supabase's transaction pooler on port 6543. `backend/dashboard.py` serves `dashboard/dist` through a Starlette `StaticFiles` that gives `index.html` for any page it has no file for, on a `Mount` after every route that takes no path under `/api/`, and none while the dashboard isn't built: the API, its wrong methods, trailing slashes and unknown paths, and `/docs`, answer as they always have. `npm run check:server` imports the backend in a temporary environment with only the `server` dependency group, the packages the deployment installs.
  - Database: SQLAlchemy Core, with the tables and every query written once in `backend/database.py` for both databases. With `DATABASE_URL` set, it is the Supabase Postgres database, through psycopg and the session pooler, with every table in the `payrollcheck` schema (`search_path` is set on each connection, in place of any `options` in the URL and keeping its other settings, such as `sslmode`) and a pool of at most 4 connections, waiting up to two minutes for one. Otherwise it is SQLite at `payrollcheck.db` or the path in `PAYROLLCHECK_DB`, with a connection per request. Each request runs in one transaction, committed before the response is sent. The tests and the end-to-end tests always use SQLite and never touch the network.
  - Sign-in: `backend/auth.py` checks a Supabase access token with PyJWT's `PyJWKClient` against the project's public keys at `VITE_SUPABASE_URL`, with the audience `authenticated` and 30 seconds of clock leeway, and returns its email; nothing else reads the address. `SignedIn` in `dependencies.py` finds the reviewer by that email (401 without a valid token, 403 for an email that isn't a reviewer's). `get_signed_in_reviewer` (`GET /api/me`) returns the reviewer with their email and whether they can sign off over the limit. Every route the dashboard alone calls needs a signed-in reviewer. Seeding stores each reviewer's email, and only Dana Whitfield can sign off over the limit.
  - The agent's API key: `backend/api_key.py` compares the key a request sends in `X-API-Key` with `PAYROLLCHECK_API_KEY`, as bytes, with `secrets.compare_digest`; with no key set nothing matches. `dependencies.py` puts one gate on every route but `health`: `AgentKey` on the operations only the agent's side calls (the case workflow, the versions it reads, the documents, and everything the service records about runs and rounds, including a round or a review for a reviewer), `ReviewerOrAgent` on the four reads both use (`list_cases`, `get_case`, `get_policy`, `get_case_history`), on `get_run`, which the agent and the Copilot's wait both read, and on `get_agent_api`, and a signed-in reviewer on everything else. The key never stands in for a reviewer. A test checks that the four lists of operations cover the app exactly once and that each operation's OpenAPI security matches its gate.
  - Read operations: `health`, `list_cases`, `get_case`, `get_policy`, `get_case_history`, `get_settings`, `list_steps`, `get_current_version`, `get_version`, `get_screening`, `get_configuration`, `get_version_details`, `get_latest_dispatch`, `list_evaluations`, `get_evaluation`, `get_agent_api`.
  - Settings: `settings` keeps the platform's settings as a history, one row per change with who made it and when; the newest row is in force. Seeding makes row 1 with the approval limit from `data/company.json` and the rest from `data/improvement.json`: the objectives on the held-out set, the noise and the tolerance, the spending limit for each round and the payroll agents at once in the improver's evaluations. `data/models.json` gives the models the payroll agent may use, with their reasoning efforts and prices, seeded into `models_allowed` (with `MODEL_NAME` set, that model alone at `default` and a price of 0). `get_settings` returns the settings in force, every change and the models allowed; `change_settings` (`PUT /api/settings`) records a new row, and only a reviewer who can sign off payouts over the limit may use it (`compliance_manager(action)` in `dependencies.py`, which names the action in its 403).
  - The judge: `backend/judge.py` is the one module that calls Jev (`typesafe/jev-1.13`) through OpenRouter's Decisions endpoint with the `openrouter` package, at `JUDGE_URL` or `https://openrouter.ai`, with the lab's rubric and three questions, a 10 second timeout and no retries. It grades the agent's reason and section against the reviewer's reason and reference, which seeding stores in `reviewer_decisions`; the score is Jev's score from 0 to 3, the letter the likeliest level, and the two checks, same grounds and same section, are kept as probabilities. `finish_run` grades an evaluation's copies in parallel, one thread each, before it finishes: an undecided copy gets an F without asking the judge, and a copy the judge can't grade is recorded with no grade and logged. `grades` holds each copy's grade and the judge's cost. An evaluation's grade averages its graded copies, and its judge cost is apart from its model cost. With `MODEL_NAME` set there's no judge, and nothing is graded.
  - The payroll agent's own API: `get_agent_api` (`GET /api/agent/openapi.json`, for the key or a signed-in reviewer) returns the OpenAPI document of the six operations the payroll agent's tools and its payment call, `get_case`, `get_policy`, `get_case_history`, `calculate_payout`, `record_decision` (whose body requires `decided_by`) and `pay_case`, built in `backend/agent_api.py` with FastAPI's `get_openapi` from the app's own routes, with their operation ids and one-line descriptions. It has no `servers`, which the deployment adds, and no security schemes, which a Gateway's OpenAPI target doesn't support; the Gateway's credential provider sends the key. A case whose next step is the pause resumes with its reviewer's answer, whether the pause has run or not: LangGraph 1.2.12 keeps an answer given before the pause as a write the pause's `interrupt()` returns at once. `work_in_run(case_id, run_id, new_agent)` builds a payroll agent (its graph, route and maker) and carries the case on if it is in progress, as a sent-back case the dispatch took is, or starts it if it is waiting: it's the one function the dispatcher calls. A case whose work has ended has nothing left to run.

## Known gaps

- Rate determinations are conclusive for two years from issue, after which a new one applies. Every date in both payroll worlds is well inside two years of its award, so `context/wage_rules.py` doesn't handle the expiry.
- The tiny set's arithmetic family is on two cases: PC-0712, and PC-1210, which also holds the unregistered apprentice.
- `e2e/copilot.spec.ts`'s narrow-window test sometimes fails under load, "Not on the page" after about 250 ms, because `boxOf` reads the sidebar's bounding box before it is laid out instead of waiting for it. It failed twice in stage 1's runs of `npm run check` and passes when run again.
- A sign-off whose resume fails, because the call to the agent fails or the resumed work does, isn't remembered: the case is paid, but the agent's work on it isn't finished, so it isn't saved to memory.
- A resume that fails, such as on a rate limit, isn't tried again: it's logged, and the next dispatch carries the case on once the resume has been quiet for five minutes.
- A request that asks the agent for something, such as a sign-off or a start, holds its database connection until the agent answers, up to 10 seconds, while the agent may call the app back before it answers. With the laptop's four connections, several such requests at once while a dispatch is busy could wait out the 10 seconds; nobody has seen it happen.
- A case with a decision but nothing saved on its thread, which only happens when someone approves a case through the API by hand, can't be carried on: each run logs the error and leaves it in progress.
- If two processes carry the same case on at the same moment, which the harness can't rule out, the backend still decides and pays it once. The second process's decision or payment, arriving while the first is being saved, is refused with an error, and that process logs it.
- A reviewer signs off a held payout or sends it back to the agent; declining one outright comes later.
- Work the app marks stopped as quiet isn't told: an agent still alive whose heartbeats were failing keeps working, and the next dispatch can pick up the same cases in progress. The backend still decides and pays each case once, as when two processes carry the same case on.
- A sign-off on a case that never paused, because its process stopped after the decision and before the pause, stands and is paid, but isn't remembered either.
- A sent-back case whose resumed work fails before a new decision goes back to the queue, and the dispatch works it afresh, as a new attempt on a new thread, without the note.
- A case stopped between its approval's tool call and the save of that step, then sent back, carries on from that tool call without the note: the app refuses the old approval, since the send back cleared its calculation, and the model works on from the refusal.
- The dispatcher's worker re-raises a rate limit or a timeout until its last try, rather than using LangGraph's `error_handler`: in LangGraph 1.2.12 a handled error is still raised from `invoke` when the worker runs beside others. A test records this, so a release that fixes it shows up.
- `uv run -m agent CLM-1001` beside a dispatch can work the same case at the same moment; the backend still decides and pays it once.
- At 25 payroll agents at once each step outside the model takes about 2.6 times as long as at 3 (0.37 against 0.14 seconds), most likely from waiting on the 4 connections a process to Supabase (see the live run below). The model itself is no slower.
- GPT-6 Luna sometimes ends its turn with a message instead of recording a decision: 4 times in the live runs below. The harness fails that attempt and the dispatch works the case once more. A case this happens to twice is left for a reviewer, as CLM-1017-E3 was.
- Langfuse loses the traces of cases stopped by `kill -9` before the service's client sent them.
- An improver call answered just as a reviewer stops the round isn't recorded, since a stopped round records nothing more, so the round's cost can be short by that one call. The stretch ends there.
- `/docs` and `/openapi.json` stay open. They describe the routes and grant nothing.
- Two compliance managers saving the settings at the same moment: the later save is built on the settings as its page loaded them, so it can undo the other's change.
- In a production build the page can paint once before `theme.ts` sets a saved appearance that differs from the computer's.
- A refused sign-off says the approval limit in force now, not the one the payout was held under, if they differ.
- An approval within the limit that isn't paid yet, because its payment failed or the agent stopped just before paying, can't be paid if the limit is lowered below it meanwhile: `pay_case` checks the limit in force before it reads the case, as the Gateway's Policy will, and only a payout held when it was decided can be signed off. It stays in progress for a reviewer. A test records this.
- The Improvement page re-scores every round's evaluations on each two-second refresh, which grows with the rounds run.
- A case's decision arriving moves the agent's steps below it down once, by the decision's height: it's new content, and keeping room for a decision would leave a large empty panel on every case. While an evaluation runs, a copy's own cost and time grow in place in their right-aligned cells.
- Rounds can't run on free models, which allow fewer requests in a day than a round needs; students on free models build and test everything.
- Stopping `npm run dev` with SIGTERM twice left a uvicorn reloader holding its port with no worker; `kill -9` on it cleared the port.
- The data dictionary in `context/` doesn't describe a decision's `gateway_refusal`; it's data governance's file, so it's left as it is.
- AgentCore turns a saved case into memories in the background, about 90 seconds after the save in our team's experiment, so a subcontractor's next case worked straight away may not find the first.
- A crash after a case is decided or held and before `remember` finishes loses that case's memory, or keeps only its first event: the dispatcher only carries on cases in progress, so nothing runs `remember` again. An approval stopped before its payment is carried on, paid and remembered once.
- `uv run -m agent` on an evaluation's copy, which nothing does, would work it with the memory: memory follows the kind of run, and a case worked on the command line has none.
- The live runs used the direct route with memory off; the Gateway's names, its refusals and the memory are covered by the tests with stand-ins, and by the deployment notebook.
- A Copilot turn that works past its sign-in's hour, such as two long waits in one turn, is refused by the app partway. With the sign-in gone, the Copilot can't tell the app either, so the turn stops there, its card still spinning, and shows as working until it reads as stopped, 20 minutes after it started. The sidebar renews a sign-in with less than 20 minutes left before it sends, which covers one 15-minute wait.
- A Copilot turn stopped partway, such as when its process dies, shows as stopped only 20 minutes after its start or its confirmation's answer.
- The Copilot's records take the reviewer's sign-in, so a reviewer could write to their own conversation's records through the API, adding cards or an answer. Nothing in them pays or decides: the sign-off and every other action go through the app's own operations and rules.
- Explaining a case's decision, the Copilot on GPT-6 Luna at `low` reads the case, the payroll agent's steps, the policy and the settings, and quotes the sections the agent cited, but in the live run never read the context layer itself unless asked to check a section, though its instructions set that goal, first as what to draw on and then as when an explanation is done. Making it hold would take code, such as a case read that brings the sections the decision cites from the context layer.
- The 15-second read on the Runtime route hasn't been measured live. A cold Copilot session that takes longer to fetch its credentials, open its pool and check the sign-in and the turn would give the reviewer a "may have started" 503, though the turn would go on.
- The Copilot's route can reach the app's tools as well as the context layer's, and the app's act as the agent; only the Copilot's tools, which take the context layer's alone, keep it from them. On Runtime, the Gateway's Policy should keep the Copilot's role to the `payrollcheck-context___` tools.
- A held decision that changes between the reviewer's answer to a confirmation and the Copilot's sign-off, a few seconds later, is signed off as it then stands, as on the case's page between loading it and pressing Sign off.
- A first message the Copilot doesn't take leaves its conversation, with the turn failed and the reason, in the earlier conversations, while the sidebar shows the reason under the box and stays on the greeting.
- AgentCore turns a conversation into the reviewer's memories in the background, about a minute and a half after the save, so a new conversation straight away may not find what the reviewer just said.
- A Copilot that stops after saving its pause and before telling the app leaves the graph waiting for an answer while the app shows the turn working, with no confirmation card, until it shows as stopped.
- A Copilot that stops after saving its result and before telling the app leaves the sidebar without the answer, or a confirmation's outcome, that the saved graph already has, though a sign-off may have paid or the memory saved. The turn shows as working and then stopped, and nothing puts the two together; a confirmation card whose sign-off began says its outcome is not known, and the case's page says whether it was paid.

## Supabase

The backend's tables and the checkpointer's are in the `payrollcheck` schema. Row Level Security is off on them, and Supabase's table listing warns about that, but the schema isn't exposed through Supabase's Data API: the `anon`, `authenticated` and `service_role` roles have no access to it, and Supabase's security advisor reports nothing. The backend and the agent connect as `postgres`, the tables' owner.

## Review of the harness

On September 30, 2026, the head of engineering's review (`docs/HUMAN_REVIEW_HARNESS.md`) found that the harness was unfit for a PR:
- The agent had more than 20 hard-coded backend URLs and two ways of calling the backend.
- `queue.py` reached into `main.py`.
- The tools were spread across files, and state was passed through closures instead of LangChain's `context_schema`.
- The instructions were step-by-step scripts.

The agent was rebuilt as `api.py`, `tools.py` and `harness.py`, and the instructions were rewritten as goals. Fresh reviewers then went through the backend, the dashboard and the tests, and their fixes are in the same change.

These problems passed every check. Each phase was built, checked against its criteria and committed, and nobody read the code the way a reviewer reads a PR. `docs/CODE_STANDARDS.md` now sets the structural rules the review found broken. `docs/PROCESS.md` now requires a review by a fresh subagent before every commit, and a design in every plan.
